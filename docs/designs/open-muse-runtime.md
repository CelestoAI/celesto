# Design: OpenMuse — Authoritative Conversation Runtime

OpenMuse should behave like one coherent computer coworker: the browser, backend, and UI must agree about what is happening, and ordinary public-web research should not stop for unnecessary approvals.

Generated by `/plan-eng-review` on 2026-09-17
Branch: `feat/openmuse-celesto-cloud`
Status: APPROVED
Mode: Builder

This design supersedes:

- the conversation lifecycle, UI synchronization, approval flow, and HTTP/event contract in [open-muse.md](open-muse.md);
- the approval policy and approval lifecycle in [open-muse-general-web.md](open-muse-general-web.md).

The computer-provider boundary, Celesto/Celesto lifecycle, browser isolation, network restrictions, durable operation journal, and viewer security in the existing designs remain authoritative.

## Outcome

Replace the current collection of partially overlapping state flags with one server-owned conversation runtime. React renders a complete server projection and sends commands. It does not reconstruct lifecycle rules. A confirmation-required browser tool remains suspended until the user approves, rejects, interrupts, or the process restarts.

The rewrite stays intentionally small:

- no XState or workflow framework;
- no event sourcing;
- no bidirectional application websocket;
- no generic policy language;
- no provider rewrite;
- no model-evaluation expansion.

## Why the current architecture fails

The current implementation has multiple sources of truth:

- `ConversationContext` independently stores `runState`, `controlOwner`, `sessionLifecycle`, and `pendingApproval`.
- `ConversationManager` additionally owns transition booleans, active promises, a turn queue, and the current execution.
- React adds local conversation, approval, trace, and viewer-pending states.
- Conversation SSE events cause snapshot refetches while traces update through a separate stream.

The approval path exposes the structural bug. `ActionBroker.runWebOperation()` returns an `approvalRequired` object to the model. The model turn is then allowed to complete and append assistant text while the backend separately holds a pending approval. On approval, the manager begins another model prompt containing serialized browser output. The result can be a browser that has moved, an assistant asking for approval, and a UI approval card that disagree with one another.

Verified findings:

- **\[P1\] (confidence: 10/10)** `open-muse/server/broker.ts:164` returns `{ approvalRequired: true, ... }` from a confirmation boundary instead of suspending the tool call.
- **\[P1\] (confidence: 10/10)** `open-muse/server/manager.ts:692-708` appends assistant output before checking `pendingApproval`, allowing confirmation prose to become a normal assistant message.
- **\[P1\] (confidence: 10/10)** `open-muse/server/manager.ts:429-448` creates a synthetic second model prompt after approval rather than completing the original tool call.
- **\[P1\] (confidence: 10/10)** `open-muse/server/types.ts:50-63` and `open-muse/server/manager.ts:47-62` define overlapping mutable lifecycle authorities.
- **\[P2\] (confidence: 10/10)** `open-muse/client/App.tsx:76-108` maintains two event streams with different update rules, while conversation events are only invalidations that cause another HTTP fetch.

## Architecture

```text
React
  ├── renders the latest ConversationView verbatim
  ├── enables only server-provided availableCommands
  └── sends typed HTTP commands
                    │
                    ▼
ConversationManager
  ├── conversation history and selection
  ├── model/provider selection
  └── delegates active work
                    │
                    ▼
ConversationRuntime (one per active conversation)
  ├── one serialized command queue
  ├── one canonical activity state
  ├── invokes model/browser/computer effects
  ├── persists recoverable state and operation outcomes
  └── publishes bounded ConversationView snapshots
             │                     │
             ▼                     ▼
       ActionPolicy          Existing adapters
       allow/confirm/deny    provider, browser driver,
                            operation journal, state store
```

Only `ConversationRuntime` may change conversation activity. Effects report completion back as runtime commands; they do not mutate shared state directly.

### Minimal module boundaries

1. `ConversationManager` remains the HTTP-facing facade for conversation history, activation, and model/provider selection.
1. `ConversationRuntime` owns active state, command serialization, interruption, model turns, confirmations, browser effects, and cleanup.
1. `ActionPolicy` is a pure `ProposedAction -> allow | confirm | deny` function.
1. `projectConversationView()` is a pure redacting projection.
1. The existing broker becomes a browser executor. It executes decisions but does not own approval or conversation state.

Do not create separate services for approvals, control, traces, viewer state, cleanup, and model turns. They are runtime transitions, not independent domains.

## Canonical state

```ts
type ConversationActivity =
  | { kind: "idle" }
  | { kind: "model_running"; turnId: string; userMessageId: string }
  | { kind: "awaiting_confirmation"; turnId: string; action: PendingAction }
  | { kind: "browser_running"; turnId: string; actionId: string }
  | { kind: "human_control"; controlEpoch: string }
  | { kind: "recovering"; recovery: RecoveryState }
  | { kind: "stopping" }
  | { kind: "stopped" }
  | { kind: "failed"; error: PublicError };
```

Computer, browser-automation, and viewer health remain separate projections because they can fail independently:

```ts
interface RuntimeState {
  version: number;
  activity: ConversationActivity;
  computer: ComputerState;
  automation: AutomationHealth;
  viewer: ViewerHealth;
  messages: Message[];
  turns: TurnTrace[];
  operationJournal: OperationRecord[];
}
```

This separation permits a healthy live display to remain visible when CDP initialization fails, and permits an agent to keep working when only the display connection needs renewal.

### Commands

All external input and effect completion enters through `dispatch(command)`. Commands are processed one at a time.

```ts
type ConversationCommand =
  | { kind: "send_message"; commandId: string; text: string }
  | { kind: "approve"; commandId: string; actionId: string; digest: string }
  | { kind: "reject"; commandId: string; actionId: string; digest: string }
  | { kind: "take_control"; commandId: string }
  | { kind: "return_control"; commandId: string; controlEpoch: string }
  | { kind: "interrupt"; commandId: string; reason: InterruptReason }
  | { kind: "stop"; commandId: string }
  | { kind: "effect_completed"; effectId: string; result: EffectResult }
  | { kind: "effect_failed"; effectId: string; error: RuntimeError };
```

The runtime derives legal commands from the current state. The public projection includes them so the client never reimplements guards:

```ts
interface ConversationView {
  conversationId: string;
  version: number;
  activity: PublicActivity;
  computer: PublicComputerState;
  viewer: PublicViewerState;
  messages: PublicMessage[];
  turns: PublicTurn[];
  availableCommands: PublicCommandKind[];
}
```

Unknown, stale, or illegal commands return a short actionable `409`. Repeated command IDs return the prior accepted result when safe.

## Model and approval flow

```text
model calls browser tool
          │
          ▼
runtime proposes typed action
          │
          ▼
ActionPolicy
  ├── allow ─────► execute ─────► resolve original tool promise
  ├── deny ──────► resolve original tool promise with refusal
  └── confirm ───► activity = awaiting_confirmation
                         │
                         ├── approve ─► execute exact action ─► resolve promise
                         ├── reject ──► resolve promise with rejection
                         ├── interrupt ► abort turn and reject promise
                         └── restart ──► restore as recovering; never replay
```

The model never receives `approvalRequired`. The runtime owns confirmation copy and the UI card. While confirmation is pending:

- no assistant completion is appended;
- no later tool can dispatch;
- the original in-process tool promise remains pending;
- approve/reject is bound to the exact action ID, digest, tab epoch, page binding, and turn;
- a new message, conversation change, model change, takeover, or Stop interrupts the pending turn;
- process restart discards the promise, marks the turn interrupted, and requires explicit Continue or Start over.

Approval execution continues through the existing durable operation journal:

```text
approved → dispatched → completed
                    └─► outcome_unknown
```

No operation saved as dispatched is automatically replayed.

## Browser action policy

The policy classifies real-world effects instead of browser mechanics.

### Allow

- observe, extract, and scroll;
- back/forward within public HTTP(S) browsing;
- navigation to a validated public HTTP(S) URL;
- safe link traversal by resolving a public `href` and navigating directly, without firing arbitrary page click handlers;
- an atomic search operation that fills a recognized searchbox and submits that search;
- browser/display reconnection that does not repeat a page action.

### Confirm

- sending or publishing content;
- adding, changing, or removing cart items;
- creating, modifying, or deleting remote data;
- uploads and downloads;
- account, subscription, booking, or permission changes;
- ordinary form submissions and buttons whose effect cannot be proven read-only;
- ambiguous actions.

### Deny or require takeover

- passwords, payment details, one-time codes, recovery information, and other secrets;
- CAPTCHA solving;
- private, loopback, link-local, reserved, metadata-service, `file:`, and browser-internal destinations;
- raw JavaScript, raw CDP, arbitrary Playwright programs, and policy changes;
- purchases or payment submission.

The policy is a pure switch over typed actions and trusted target metadata. Do not add site adapters, trust scores, or model-authored policy decisions in this rewrite.

## Public-web tool contract

Prefer semantic actions that make the policy obvious:

- `browser_observe()`
- `browser_extract(scopeRef?)`
- `browser_scroll(direction)`
- `browser_navigate(url)`
- `browser_follow_link(ref)`
- `browser_search(ref, query)`
- `browser_interact(proposal)` for effectful or ambiguous click/fill/select/key actions

`browser_follow_link` navigates to the resolved public URL rather than clicking the page element. `browser_search` is one atomic operation; it avoids tracking a partially filled field merely to decide whether a later Enter key is safe.

## Client and transport contract

Use HTTP for commands and one SSE stream for bounded full views.

```text
GET  /api/conversations/:id       → current ConversationView
GET  /api/conversations/:id/views → SSE full ConversationView snapshots
POST /api/conversations/:id/commands
     { commandId, expectedVersion?, command }
```

Existing convenience endpoints may temporarily translate into commands inside `ConversationManager`, but React should use the command endpoint only. Remove those adapters before the PR merges unless an external consumer is documented.

Every meaningful transition publishes the latest full view. React replaces its previous view wholesale. It does not apply business transitions locally. SSE reconnect returns a full current view, so there is no patch-replay protocol and no `Last-Event-ID` dependency for correctness.

Trace updates are folded into the same view. Rapid trace-only changes may be coalesced, but activity, confirmation, control, error, and message transitions publish immediately.

The viewer remains a separate iframe/websocket transport. The view contains only viewer health and whether a fresh token may be requested. API keys, provider connection URLs, CDP URLs, display tokens, screenshots, accessibility trees, and page text never enter the view.

## Interruption semantics

Conversation switching, creating a new chat, changing models, takeover, a new user message, and Stop interrupt current model work instead of asking the user to wait.

```text
interrupt command
  ├── atomically prevents the next dispatch
  ├── aborts the model request
  ├── rejects any suspended tool promise
  ├── invalidates pending action, grants, and browser refs
  ├── waits only for an already-dispatched atomic browser effect
  ├── records unknown outcome when completion cannot be proved
  └── settles into the requested next state
```

The runtime command queue serializes the transition. React needs no `conversationPendingRef` or inferred busy guard; it disables controls from `availableCommands` and may show a command-specific pending label until the next view version arrives.

## Persistence and restart

Persist only serializable domain state:

- bounded messages and turn summaries;
- selected model/provider;
- Celesto computer reference where applicable;
- computer lifecycle required for reconnect;
- durable operation journal and recovery state;
- canonical activity normalized for restart.

Never persist promises, abort controllers, agents, Playwright handles, connection URLs, tokens, credentials, pending confirmation capability, or raw page data.

Restart normalization:

| Saved activity | Restored activity |
|---|---|
| `idle` | `idle` |
| `model_running` | `recovering(interrupted)` |
| `awaiting_confirmation` | `recovering(interrupted)`; discard action capability |
| `browser_running` before dispatch | `recovering(failed_before_execution)` |
| `browser_running` after dispatch | `recovering(outcome_unknown)` |
| `human_control` | `recovering(interrupted)` |
| `stopping` | finish cleanup, then `stopped` |
| `stopped` | `stopped` |

The existing provider reconnect logic should restore a Celesto computer only when its status remains usable. Missing, deleting, or deleted cloud computers become `recovering(computer_unavailable)`.

## Failure modes

| Failure | Handling | Test | User result |
|---|---|---|---|
| Duplicate or stale command | command ID dedupe and optional expected version | runtime contract | actionable `409` or prior result |
| New message during model work | interrupt before accepting new turn | runtime + E2E | new request replaces old work |
| Conversation/model change during confirmation | interrupt suspended tool and invalidate action | runtime + E2E | requested change proceeds |
| Double approval | action ID/digest and command dedupe | runtime + HTTP | action executes at most once |
| Restart during confirmation | restore as interrupted; never replay | persistence integration | Continue/Start over recovery |
| Crash after browser dispatch | durable journal marks unknown outcome | operation integration | warns user to inspect before retry |
| CDP token expires | re-mint once through provider and reconnect | provider integration | one reconnect, then clear error |
| CDP fails while display is healthy | independent automation/viewer health | projection + E2E | display remains visible with browser error |
| Viewer websocket drops | fresh display connection on reconnect | viewer integration | reconnect control without repeating work |
| Celesto computer was deleted remotely | normalize reference to unavailable | provider integration | Continue creates a fresh computer |
| SSE disconnects or misses updates | reconnect receives a full current view | HTTP/SSE integration | UI converges without patch replay |
| Persisting a transition fails | do not acknowledge success; enter recoverable failure | runtime integration | concise retry/start-over action |
| Full view exceeds bound | message/turn compaction and 256 KB assertion | projection unit test | no silent degradation |

No identified failure is intentionally silent. The implementation is not complete until each row has both handling and a test.

## Implementation order

The rewrite lands as one PR but is implemented in dependency order.

1. Define the canonical runtime state, commands, transition reducer, public view, and table-driven tests. Do not connect effects yet.
1. Move model, computer, browser, confirmation, control, cleanup, and persistence orchestration behind `ConversationRuntime`. Keep existing providers, browser driver, state store, and operation journal.
1. Replace broker-owned approval with a suspended tool promise. Add the pure effect-based policy and semantic follow-link/search actions.
1. Route all mutations through commands. Publish full views through one SSE stream and preserve viewer websocket isolation.
1. Replace React lifecycle inference with one view subscription and server-provided `availableCommands`. Remove local approval/conversation locks and the separate trace stream.
1. Migrate persistence and restart normalization to canonical state, including Celesto computer reconnection and unknown-effect recovery.
1. Replace obsolete tests, add the complete runtime/integration/E2E matrix, remove compatibility paths, and update both older design documents.

Structural and behavioral changes should be committed separately while developing, even though they ship in one PR: first the runtime types/reducer, then effect integration, then transport/client migration, then cleanup.

## What already exists

- `computer-provider.ts` already provides the correct Celesto/Celesto boundary and persists Celesto references; reuse it unchanged except for runtime callbacks.
- `browser-driver.ts` already validates and executes structured operations; reuse it as the low-level executor.
- `operation-lifecycle.ts` already models approved/dispatched/completed/unknown outcomes; keep it as the durability boundary for consequential effects.
- `state-store.ts` already performs bounded atomic checkpointing and secret redaction; migrate its schema rather than replacing storage.
- `trace.ts` already correlates turns and steps; project it into `ConversationView` instead of maintaining a second client stream.
- the viewer proxy already re-mints Celesto display connections and separates read-only/read-write modes; retain that path.
- conversation-change interruption, bootstrap retry, dev startup ordering, and shutdown connection cleanup already solve real regressions; preserve their behavior through runtime commands.

## NOT in scope

- Rewriting the Celesto or Celesto computer providers: their protocol boundary is already correct.
- XState, event sourcing, workflow engines, queues, databases, or distributed coordination: unnecessary for a loopback single-user app.
- Remote multi-user OpenMuse hosting and authentication: the application remains loopback-only.
- Incremental client patches or a bidirectional command websocket: full bounded views are simpler.
- Site-specific adapters, learned trust scores, and model-authored policy: the policy remains deterministic and typed.
- Authenticated profile expansion, shell/file tools, payments, or automatic purchasing: these retain their existing security gates.
- New live-model or cross-model evaluation cases: explicitly declined; deterministic and E2E coverage carries this rewrite.
- Visual redesign: only state correctness, command availability, and confirmation copy change.
- New distributable artifacts or release pipeline changes: this modifies the existing OpenMuse example only.

## Parallelization

Sequential implementation, no parallelization opportunity. The runtime state and public view define the contracts consumed by approval, transport, React, persistence, and tests; parallel worktrees would repeatedly collide in the same server and client modules.

## Completion criteria

1. Public navigation, safe link traversal, and search complete without approval.
1. Consequential actions produce one UI confirmation and no assistant confirmation message.
1. Approval continues the original tool call and cannot repeat the exact action.
1. A new message, chat switch, model switch, takeover, or Stop interrupts current model work.
1. React renders only the latest server view and uses `availableCommands`; it contains no lifecycle policy.
1. SSE reconnect converges with one full view and traces cannot disagree with conversation state.
1. Viewer and browser-automation health remain independently visible.
1. Restart never replays a pending or dispatched effect.
1. Celesto and Celesto Cloud pass the same runtime lifecycle contract.
1. All failure modes above have deterministic tests and actionable user-facing errors.
